# Venom app AI gateway

- **Credential boundary.** Gateway credentials exist only behind the provisioning provider boundary: minted server-side at handoff or rotate, delivered straight into the app's secret storage — never through chat, clients, or exports. Handoff preparation fails open to defer: a delivery hiccup must not block provisioning; the credential lands on the next handoff or an explicit rotate.
- **Alias-only surface.** The gateway accepts and emits Venom aliases only. Provider SKUs, keys, and account details never appear in payloads or errors; provider billing trouble keeps the sanitized, non-retryable provider_account shape shared with in-product chat.
- **One canonical ledger.** The per-call app-AI ledger (owner, app, alias, tokens, cost basis in integer micro-dollars) is THE usage record future billing prices on. In-product chat metering is a separate system until deliberately migrated — don't "helpfully" merge them.
- **Caps enforce by reservation, never read-then-act.** Reading month spend and then dispatching lets parallel calls all pass the same below-cap read. The gate reserves the request's priced worst case — a conservative prompt bound plus the output ceiling actually forwarded to the provider — inside one per-app locked transaction, admitting only when the whole bound fits the remaining headroom; settlement releases the reservation in the same transaction that writes the ledger row, under the same per-app spend lock the gate takes — an unlocked settlement can commit between the gate's separate aggregate reads (Read Committed: one snapshot per statement) and vanish from both counts. Flat reservations fail both ways: real cost can exceed the hold, and a nearly spent cap still admits one more call. Age-reap leaked reservations so a crash cannot wedge an app until month end.
- **The whole credential lifecycle is serialized.** Revoke-then-insert alone can leave two live tokens under concurrency — and an unlocked revoke racing a rotation can leave a live credential after the owner saw revoke succeed. Mint, rotate, AND revoke share one per-app advisory lock, with a partial unique active-credential index as the DB backstop and one retry on backstop conflict. Provider secret delivery runs inside that same lock behind an is-still-active re-check: a delayed stale delivery skips instead of clobbering the newer key, a racing mint waits out an in-flight delivery, and the handoff package never carries the secret — every provider secret write goes through the one serialized guard.
- **Why:** both races are financial-abuse vectors — duplicate live credentials widen a leak's blast radius, and cap overspend is real money against the owner.
- **"No cap" is null, never 0.** The cap editor's minimum is a positive amount; clients always send the full settings body.
