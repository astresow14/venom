---
name: Orval generated normalization
description: Why generated API files must be regenerated after contract merges and checked for unstable tails.
---

Regenerate Orval outputs after any merge or rebase that touches the OpenAPI contract or generated files; never trust a textual merge of generated Zod output. Then inspect generated TypeScript with `git diff --check`. The generator leaves extra blank lines at EOF, but the codegen pipeline's post-generation normalization trims them: regeneration is byte-stable on an unchanged spec (two consecutive runs produce zero diff), so no `export {};` terminator hacks are needed.

Orval itself (v8.x) can also emit a literal helper constant (`fooNameMax = 200`) AFTER the schema that references it — a deterministic generation-order bug that typechecks clean but throws a temporal-dead-zone ReferenceError the moment anything imports the zod module at runtime (every ESM test suite dies at module evaluation; esbuild-bundled CJS tests can mask it by reordering). The codegen script now runs api-spec/scripts/hoist-literal-consts.mjs after orval, which hoists all dependency-free literal consts below the imports and normalizes EOF blank lines in both generated trees — keep that step in the pipeline, and prove fixes with a direct dynamic-import probe, not typecheck alone.

**Why:** A textual merge can reorder generated schema constants, causing compile-time use-before-declaration errors or runtime `undefined` validators. Successful generation and typechecking still do not catch the separate whitespace failure, and repeated generation can restore it.

**How to apply:** After contract merges, run the canonical OpenAPI codegen command instead of repairing generated files by hand. Normalize only generated tails afterward, rerun the full typecheck and contract-backed tests, and require `git diff --check` before completion. For route-critical generated schemas, keep a direct import-and-parse regression because typechecking may pass while runtime initialization still supplies an undefined validator.

Out-of-order constants are not merge-only: a zod output has shipped with two new operations' constants interleaved so a RegExp was declared *after* the schema using it, and `tsc --build` still passed. Bundled (esbuild-CJS) tests lower the TDZ to an `undefined` validator — routes 500 only when the schema parses — while `--experimental-strip-types` runs throw `ReferenceError ... before initialization` at import. After any codegen that adds operations, run a strip-types suite that imports the generated file (it fails loudest), or grep that each new `...RegExp` declaration precedes its first use; re-running codegen fixes the order.

Cross-package drift: the one spec (lib/api-spec/openapi.yaml) generates two sibling copies — api-zod's types and api-client-react's api.schemas.ts. A replayed auto-merge can revert one copy while the other stays current, and nothing fails until some consumer file happens to reference the missing surface (the client package exports raw src, so no build step notices). Symptom: a consumer typecheck error on a generated property that plainly exists in the yaml and in the sibling package. Fix is never hand-editing: `pnpm --filter ./lib/api-spec run codegen` regenerates both; expect a large diff when the stale copy missed several merges, then rerun the full workspace typecheck.

Drift is now gated: the `codegen-freshness` validation command (api-spec's `check:freshness` script) checks HEAD out into a disposable git worktree (borrowing real node_modules via symlinks), reruns the generation pipeline (`codegen:generate` = orval + hoist), and fails on any `git status --porcelain` change under either generated dir, plus an empty-tree `git diff --check` enforcing the EOF-tail normalization on all current content. If it fails after a merge, the committed copies are stale — regenerate and commit; byte-stability means a passing tree stays passing. The gate deliberately skips codegen's `typecheck:libs` tail: workspace-package symlinks under borrowed node_modules realpath outside the worktree, which strips project-reference redirects and yields bogus type errors — and typecheck never changes the freshness verdict anyway. `CODEGEN_FRESHNESS_REF` gates a commit other than HEAD.

Consumer-side gotcha: this workspace's generated react-query hooks type their `query` options so an explicit `queryKey` is required — call `useGetX(..., { query: { queryKey: getGetXQueryKey(...), ... } })`. Omitting it is a type error even though vanilla react-query would infer it; both clients already follow this convention.
A task merge can also land regenerated output produced from a mid-rebase spec, silently dropping fields the current spec still declares (typecheck breaks in consumers, runtime validators strip the fields). When hand-written code references fields the generated types lack, run the canonical codegen from HEAD's spec before debugging the hand-written side — it can fix typecheck and runtime in one step.

Signature-shift gotcha: adding query parameters to an existing operation inserts a `params` argument before the trailing options argument in generated fetchers and hooks, so call sites that passed `{ headers }` or `{ query }` positionally fail type-check in files the spec change never touched; after regenerating, revisit that operation's call sites and pass explicit `undefined` params.

Contract conventions the generator enforces: response-body numerics are `type: number` — `type: integer` is only safe on coerced query/path params, because generated integer response validators use a zod API this workspace's zod version lacks. Non-JSON download responses must use a `text/*` media type so the generated function returns the body string (the markdown and JSONL exports both do this); an unrecognized media type such as application/x-ndjson generates a `Response`-typed fetcher the shared fetch layer never satisfies — it parses bodies and hands back a Blob. Timestamps must be spelled `type: string, format: date-time`; other spellings on time-like fields (a stray `format: uuid`, an integer epoch) have made orval emit zod-v4-only validator calls that break under the workspace's zod 3.25 — fix the spec spelling and regenerate, never patch the generated output.

- The freshness gate regenerates in an isolated worktree against the COMMITTED tree: with regenerated-but-uncommitted client files it still fails locally. That state is fine — the completion flow commits the working tree first, then validation sees fresh copies.
